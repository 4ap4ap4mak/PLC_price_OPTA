# CLAUDE.md — вход для ИИ-агентов

Этот файл первым читает ИИ-агент (Claude Code и другие), который работает с проектом.
Людям лучше начать с [README.md](README.md).

## Что это за проект

Прошивка для ПЛК **Arduino Opta WiFi** (STM32H747, ядро Arduino mbed, PlatformIO).
Устройство раз в 15 минут берет биржевую цену электроэнергии Nord Pool для Латвии
из API Elering и управляет 4 реле (D0–D3) по сценариям: аварийный предел цены,
порог, самые дешевые часы, нагрев перед пробуждением, ночное окно, отпуск,
непрерывный (принудительный) нагрев. Настройка через веб-страницу
(`http://opta-settings.local`), Serial-консоль и кнопку USER.

## Текущее состояние (обновлять при каждом шаге)

- Весь код пока в одном файле [src/main.cpp](src/main.cpp) (~3260 строк).
- Этап 1 (критические исправления) — ветка `fix/critical-bugs`, ждет проверки на железе.
- Этап 2 — пошаговый рефакторинг по [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), раздел 6.
- Тестов пока нет. `env:native` появится на шаге 2a. Компилятор хоста (MinGW-w64)
  уже установлен.

## Команды

```sh
pio run -e opta                 # сборка прошивки (работает в среде агента)
pio run -e opta -t upload       # прошивка — делает только пользователь, плата у него
pio device monitor -b 115200    # Serial-монитор
pio test -e native              # unit-тесты на ПК (после шага 2a)
```

## Жесткие правила

1. **Агент не может проверить код на железе.** После любого изменения прошивки прямо
   скажи, что на устройстве не проверено, и перечисли, что пользователю нужно проверить.
2. **Безопасность реле важнее функций.** Реле управляют нагревом. Любое изменение,
   которое может оставить реле включенным без контроля (зависание `loop()`, пропуск
   failsafe, сброс watchdog), требует явного обоснования.
3. **Перенос кода и изменение поведения — в разных коммитах и ветках.** Рефакторинг
   должен давать бит-в-бит то же поведение, а изменения поведения сопровождаются тестами.
4. **Не чинить логику планировщика в монолите.** Сначала перенос в `lib/planner`
   с тестами (шаг 2a), потом исправления (2b).
5. **Формат настроек во flash** (`/kv/device_config`, сейчас версия 5) менять только
   с повышением версии и миграцией старых блобов. Иначе пользователь потеряет настройки.
6. **Git:** работать в feature-ветках, пушить в `origin`. В `main` сливать только после
   того, как пользователь подтвердит проверку на железе. Коммиты на английском,
   комментарии в коде и документация на русском.
7. **Документация — часть изменения.** В том же коммите обновить соответствующий
   документ: поведение → SCENARIOS/OPERATIONS, решение → DECISIONS, баг → KNOWN_ISSUES,
   модуль → ARCHITECTURE, а также раздел «Текущее состояние» выше.
8. Если пользователь просит только аудит или список — дать список и не менять код.

## Пользователь

Пишет по-русски, отвечать по-русски. Сам тестирует на физической Opta. Git и GitHub
поручает агенту. Важные продуктовые решения (поведение реле) принимает сам: если
поведение не описано в SCENARIOS или DECISIONS, спроси.

## Особенности платформы, о которых легко забыть

- `WiFiClient` и `EthernetClient` в ядре mbed наследуют `arduino::Client`. Обработчик
  можно писать для `arduino::Client&`, без шаблонов.
- `millis()` переполняется через ~49 дней. Сравнивать только как `now - start >= interval`,
  никогда `now >= deadline` (в `serviceWiredNetwork` такие сравнения пока есть,
  см. KNOWN_ISSUES).
- Аппаратный watchdog запускается в конце `setup()` с таймаутом mbed по умолчанию.
  Фактическое значение печатается при старте в строке `[WATCHDOG] ... таймаут N мс`.
  Любой цикл ожидания (сеть, HTTP, Wi-Fi) должен внутри вызывать `kickWatchdog()`.
- Время в коде — `uint32_t` epoch UTC. Местное время — только Europe/Riga
  (UTC+2/UTC+3, переход в последнее воскресенье марта/октября в 01:00 UTC).
- Elering отдает цены в **EUR/MWh**, в прошивке хранится **EUR/kWh** (деление на 1000).
  Цена может быть отрицательной, поэтому наличие цены — отдельный флаг `hasLatestPrice`.
- Пароль точки настройки `opta1234` и имя `Opta-Config-AP` захардкожены.
