# Логика управления реле

Документ описывает, **как прошивка решает, включить реле или нет**. Это контракт
поведения: любое изменение логики сначала отражается здесь.

Описано поведение кода на ветке `fix/planner` (шаг 2b). Запланированные изменения
помечены **[план]**, известные ошибки — **[баг]** со ссылкой на
[KNOWN_ISSUES.md](KNOWN_ISSUES.md). Решения пользователя, на которых держатся правила,
— D-012…D-019 в [DECISIONS.md](DECISIONS.md).

Обозначения: **интервал** — 15-минутный слот цены Nord Pool; **окно** — период, внутри
которого сценарий выбирает интервалы. Время везде местное, **Europe/Riga**.

## 1. Цикл принятия решения

```
каждые loop():
  failsafe → консоль → кнопка → сеть/веб → servicePriceSchedule()

servicePriceSchedule():
  нет времени NTP?           → повторять синхронизацию раз в 60 с, решений не принимать
  первые 60 с каждой четверти часа (:00, :15, :30, :45):
                             → сбросить ручной режим у всех реле
                             → начать ожидание новой цены
  ожидаем новую цену?        → запрос раз в 30 с, пока API не вернет timestamp новее прежнего
  получена новая цена        → обновить прогноз → план и решение для каждого реле не в ручном режиме
  раз в минуту               → план и решение для реле, у которых включен хотя бы один сценарий
                               по расписанию (умный порог, пробуждение, ночь, непрерывный, отпуск),
                               по последней цене и уже загруженному прогнозу
```

Перед каждым решением строится **план канала** (`planner::buildPlan`) на весь прогноз
(вчера–завтра) по 15-минутным интервалам. Из того же плана рисуется график (§8).

Следствия:

- Реле, у которого включен только порог, меняет состояние лишь при получении новой цены
  (раз в 15 минут).
- Если API временно недоступен, реле сохраняет последнее состояние до 1 часа (см. §5).
- Если не удался только запрос прогноза, план строится по прежнему прогнозу (D-018).
- После старта все реле выключены, пока не придет первая цена.
- После сохранения настроек на веб-странице решение для этого реле пересчитывается сразу.

## 2. Приоритеты

Сверху вниз; первое сработавшее правило определяет результат.

| # | Правило | Результат |
|---|---|---|
| 1 | Ручной режим (кнопка USER, `on`/`off` в консоли) | как задал пользователь |
| 1a | **[план]** Принудительное включение активно | ВКЛ (см. §6) |
| 2 | Нет актуальной цены больше часа (failsafe) | ВЫКЛ |
| 3 | Текущая цена > аварийного предела | ВЫКЛ |
| 4 | Отпуск включен и момент возвращения не наступил | только сценарий отпуска |
| 5 | Порог ИЛИ умный порог ИЛИ пробуждение ИЛИ ночь ИЛИ непрерывный блок | ВКЛ, если сработал хотя бы один |
| 6 | Ничего не сработало | ВЫКЛ |

Сценарии пункта 5 объединяются по ИЛИ: каждый может только **добавить** время работы,
но не запретить его. Причина решения печатается в логе и записывается в историю
переключений (§9).

## 3. Параметры реле

Хранятся отдельно для каждого из 4 реле (структура `ChannelConfig` в
`lib/channelconfig/ChannelConfig.h`, версия 5).

| Поле | Поле формы | По умолчанию | Допустимо |
|---|---|---|---|
| `safetyCeilingEurKwh` | `safety` | 0.30 | 0…100, строго больше порога |
| `alwaysOnBelowPriceEurKwh` | `threshold` | 0.00 | −100…100 |
| `smartThresholdEnabled` / `Hours` | `smart_enabled` / `smart_hours` | выкл / 4 | 1…24 |
| `wakeupEnabled` / `Hours` / `TimeMinuteOfDay` | `wakeup_enabled` / `wakeup_hours` / `wakeup_time` | выкл / 3 / 07:00 | 1…24, ЧЧ:ММ |
| `nightPrepEnabled` / `Start` / `End` / `CheapHours` | `night_enabled` / `night_start` / `night_end` / `night_hours` | выкл / 23:00 / 07:00 / 4 | начало ≠ конец; часов ≤ длины окна |
| `consecutiveBlockEnabled` / `Hours` | `block_enabled` / `block_hours` | выкл / 3 | 1…24 |
| `holidayEnabled` / `ReturnEpoch` / `holidayOnHours` | `holiday_enabled` / `return_local` / `holiday_hours` | выкл / — / 3 | дата в будущем; в форме 1…10 |

Цены в настройках — **EUR/kWh** (на графике — центы/кВт·ч). Количество часов задается
в часах, работа считается 15-минутными интервалами: N часов = 4·N интервалов.

`holiday_hours` во flash по-прежнему допускает 1…24 (формат v5 не меняется), но окно
отпуска — 10 часов, поэтому значение больше 10 работает как «все интервалы окна».

## 4. Сценарии

### 4.0 Общие правила выбора интервалов

Касаются умного порога, ночи и отпуска (D-012…D-016).

1. **Интервалы, не часы.** Сценарий выбирает 4·N самых дешевых 15-минутных интервалов
   своего окна, не обязательно подряд. Средняя цена часа не используется: внутри часа
   цена бывает от 10 до 30 центов.
2. **Только целые интервалы.** В окно входят интервалы, которые целиком лежат внутри.
   Окно 23:10–06:50 → интервалы с 23:15 до 06:30–06:45. Для отпуска — интервалы,
   закончившиеся до момента возвращения.
3. **Выбор по всему окну, один раз.** Выбор делается по всему окну, включая уже
   прошедшие интервалы, и дальше не пересчитывается (`PlannerState`, в RAM). За окно
   реле отрабатывает ровно N часов (исправлены KI-002, KI-003).
4. **Только при полном прогнозе.** Выбор делается, когда прогноз покрывает окно до
   последнего интервала. До этого сценарий реле не включает (лог `[WARN] … ждет цен`).
5. **После сбоя — тоже по всему окну.** После перезагрузки, пропадания питания или
   позднего появления цен выбор идет по всему окну. Прошедшие выбранные интервалы
   считаются отработанными, даже если реле в них не работало. Сознательный выбор
   пользователя: недобор при сбое, зато перезагрузка (например, прошивка) не добавляет
   лишних часов.
6. **Пропуски не добираются.** Если выбранный интервал «съел» failsafe, аварийный
   предел или ручной режим, он не заменяется другим.
7. **Смена настроек посреди окна** (D-013). Прошедшие интервалы, выбранные действовавшим
   планом и попадающие в новое окно, засчитываются; недостающие до нового N добираются
   из оставшихся, начиная с текущего интервала (он кандидат, даже если от него осталась
   минута; засчитывается целиком). Сценарий, включенный посреди окна, берет N из
   оставшихся. Если отработано уже больше нового N, до конца окна сценарий реле
   не включает. Сохранение, не меняющее параметры сценария, выбор не трогает.
8. **Нехватка интервалов.** Если в окне меньше 4·N интервалов (в ночь перехода на летнее
   время, при пропусках в прогнозе), выбираются все; в лог — `[WARN] … выбраны все доступные`.
9. **Равная цена.** Из интервалов с одинаковой ценой выбирается более ранний.
   Ночь и отпуск потом сдвигаются к концу окна (п. 10).
10. **Сдвиг к концу окна** (D-016, только ночь и отпуск). Каждый выбранный интервал
    переносится на самый поздний свободный интервал окна, если тот дороже исходного
    **не больше чем на 1 цент/кВт·ч**. Разница считается от исходной цены, цепочки
    переносов не накапливаются. Цель — быть ближе к пробуждению или возвращению.

Пример сдвига: ночь, N = 1. 02:00–02:45 стоит 5,0 ц, 06:00–06:45 — 5,8 ц → реле работает
06:00–07:00. Если 06:00–06:45 стоит 6,5 ц (дороже на 1,5 ц) — остается 02:00–03:00.

Частота переключений не ограничивается: реле может включаться и выключаться каждые
15 минут. Минимальное время работы — с конфигом v6 ([ARCHITECTURE.md](ARCHITECTURE.md) §8.3).

### 4.1 Аварийный предел (`safety`)

Всегда активен. Если **текущая** цена строго выше предела, реле выключено, что бы ни
говорили другие сценарии (кроме ручного режима). На графике интервалы дороже предела
не закрашиваются.

### 4.2 Порог включения (`threshold`)

Всегда активен, отдельного флажка нет. Если текущая цена ≤ порога, реле включено.
По умолчанию порог 0.00: реле включается при нулевой и отрицательной цене.
Чтобы фактически отключить правило, задайте порог −100.

### 4.3 Умный порог (`smart_*`)

Окно — текущие местные сутки 00:00–24:00 (23 или 25 часов в дни перехода времени).
Выбирается 4·N самых дешевых интервалов суток по правилам §4.0, **без сдвига**.
Цены на сегодня известны с прошлого дня, поэтому выбор делается в полночь и действует
весь день. Если самые дешевые интервалы уже прошли, сегодня реле по этому сценарию
больше не включится.

### 4.4 Включение перед пробуждением (`wakeup_*`)

Цена не учитывается, прогноз не нужен. Берется ближайшее будущее время пробуждения T.
Реле включено ровно N часов до него: `[T − N ч, T)` с точностью до минуты (D-017).

Пример: пробуждение 07:30, N = 3 → работа 04:30–07:30.

В день перехода на летнее время несуществующее время (03:00–03:59) пропускается — берется
следующий день. Аварийный предел (§4.1) и failsafe (§5) действуют и здесь.

### 4.5 Включение ночью (`night_*`)

Окно — от начала до конца ночи (например, 23:00–07:00), текущее или ближайшее
следующее. Выбирается 4·N самых дешевых интервалов окна по правилам §4.0, **со сдвигом
к концу окна**. Реле включено, если текущий интервал выбран.

- Цены на завтра появляются около 14:00, поэтому окно 23:00–07:00 выбирается заранее,
  в момент публикации.
- В ночь перехода на зимнее время окно 23:00–07:00 длится 9 часов (час 03:00 повторяется),
  на летнее — 7 часов.
- Ночное окно, которое начинается раньше публикации цен на завтра и уходит за полночь
  (например, 12:00–06:00), может отработать меньше N часов: интервалы, прошедшие до
  публикации, засчитываются (§4.0 п. 5). См. «Ограничения» в KNOWN_ISSUES.

### 4.6 Отпуск (`holiday_*`)

Окно — **последние 10 часов перед возвращением** (D-015). Пока момент возвращения
не наступил:

- до окна реле **выключено** при любой цене;
- в окне — 4·N самых дешевых интервалов по правилам §4.0, **со сдвигом к моменту
  возвращения**; реле включено только в них;
- если прогноз еще не покрывает окно — реле выключено.

10 часов выбраны так, чтобы окно было известно целиком к своему началу: цены на завтра
публикуются около 14:00, а окно начинается не раньше 14:00 накануне.

Когда момент возвращения наступает, флажок отпуска сам снимается и сохраняется во flash,
дальше работают обычные сценарии.

Отпуск **перекрывает** порог, умный порог, пробуждение, ночь и непрерывный блок.
Аварийный предел действует.

### 4.7 Непрерывный блок (`block_*`) — до шага 2c без изменений

Ищется самый дешевый непрерывный отрезок из N полных часов (по средней цене часа) от
текущего часа до конца прогноза. Отрезок фиксируется до своего окончания.

- **[баг] KI-004.** Сразу после окончания отрезка выбирается новый, и реле может
  работать почти без перерыва.
- **[план] шаг 2c.** Сценарий заменяется на «принудительное включение» по кнопке (§6).

## 5. Защита при отсутствии цены (failsafe)

Если с момента получения последней новой цены прошло **больше 1 часа**:

- флаг «есть актуальная цена» сбрасывается;
- все реле **не в ручном режиме** выключаются;
- новые решения не принимаются, пока не придет свежая цена.

Работает в любом режиме сети, включая точку настройки и полное отсутствие Wi-Fi.
Ручной режим не трогает: это явное решение пользователя. Обоснование — D-001
в [DECISIONS.md](DECISIONS.md).

Прогноз на failsafe не влияет: если не удался только его запрос, план строится по прежнему
прогнозу, пока тот покрывает текущее время (D-018).

Цена из API принимается, только если:

- ответ содержит `success: true` и числовые `price` и `timestamp`;
- цена в диапазоне −1000…10000 EUR/MWh;
- timestamp не раньше 2025-01-01;
- при синхронизированном времени timestamp не старше 1 часа. Задуман и допуск «не
  дальше 5 минут в будущем», но из-за переполнения **[баг] KI-015** отклоняется любая
  цена с timestamp позже часов устройства (повтор через 30 с);
- timestamp **строго больше** предыдущего принятого (иначе это старая цена:
  повтор через 30 с, реле не меняется).

## 6. [план] Принудительное включение на время — шаг 2c

Назначение: **аварийное включение реле по сети, не глядя на цену**. Аналог ручной
кнопки, но доступный удаленно и с автоматическим выключением по времени.
Требования пользователя — D-006, уточнения — D-007 в [DECISIONS.md](DECISIONS.md).

Поведение:

1. На веб-странице у каждого реле есть кнопка **«Включить на N ч»**
   (N — `block_hours`, 1…24, по умолчанию 3) и кнопка **«Остановить»**.
   В Serial-консоли — команды `force [1-4]` и `force off [1-4]`.
2. После нажатия реле включается **сразу** и остается включенным N часов независимо от:
   цены, аварийного предела, отпуска, отсутствия интернета, failsafe и границ
   15-минутных интервалов.
3. Включение заканчивается, когда истекло время или пользователь нажал «Остановить».
   После этого реле **возвращается в автоматический режим**, и решение принимается
   по сценариям сразу.
4. Последняя команда пользователя побеждает. Ручное `on`/`off` (кнопка USER, консоль)
   отменяет принудительное включение. Запуск принудительного включения отменяет ручной режим.
5. Повторное нажатие «Включить» во время работы отсчитывает N часов заново.
6. Таймер считается по времени работы устройства (`millis()`), поэтому не зависит
   от NTP. После перезагрузки или пропадания питания включение **не возобновляется**,
   реле выключено до первого решения автоматики.
7. Страница и консоль показывают оставшееся время. На графике оставшееся время работы
   закрашено.
8. Флажок `block_enabled` больше не используется; формат настроек остается версии 5.

## 7. Ручной режим

- Кнопка USER, короткое нажатие: переключить **реле 1** и перевести его в ручной режим.
- Консоль: `on N`, `off N` — ручной режим реле N; `auto N` — вернуть автоматику и сразу
  запросить цену.
- **Ручной режим сбрасывается на ближайшей границе 15 минут**, после чего реле снова
  управляется по цене. Это долговременное включение не заменяет — для него нужно
  принудительное включение (§6).
- В ручном режиме реле не трогают ни аварийный предел, ни failsafe.
- Ручной режим не меняет выбор интервалов: пропущенный интервал не добирается (§4.0 п. 6).

## 8. График на веб-странице

- График рисует браузер по данным, встроенным в страницу (D-020). Вкладки
  **«Вчера» / «Сегодня» / «Завтра»** переключают сутки без перезагрузки; подсказка при
  наведении показывает интервал, цену и причину плана.
- Синяя ступенчатая линия — цены по 15-минутным интервалам; шкала подстраивается под
  цены суток (отрицательные цены видны ниже нуля).
- Серые полосы — **план автоматики** выбранного реле. Решение и график берутся из одного
  и того же плана (`planner::ChannelPlan`), поэтому совпадают (исправлен KI-005).
  Аварийный предел на графике применяется к цене каждого интервала, в решении — к
  текущей цене из `/current`; для текущего интервала это одна и та же цена.
- Ручной режим на графике **не показывается**: только автоматика по прогнозу.
- «Вчера» — план, пересчитанный по **текущим** настройкам. Что было на самом деле,
  показывает история переключений (§9).
- Пробуждение закрашивает интервал, который его окно задевает хотя бы частично
  (при пробуждении в 07:10 — интервал 07:00–07:15).
- Окна, которые прогноз еще не покрывает (ночь после завтрашнего вечера, отпуск без
  цен), не закрашиваются.
- Красная пунктирная линия и точка — текущее время и текущая цена (только «Сегодня»).

## 9. История переключений

- Каждое **изменение** состояния реле записывается с временем и причиной: сценарий
  («Включение ночью», «Порог включения»…), «Ни один сценарий не выбрал интервал»,
  «Аварийный предел цены», «Нет актуальной цены больше часа», «Ручной режим»,
  «Отпуск: интервал не выбран». Плюс событие «Запуск устройства».
- Хранится в оперативной памяти, **до перезапуска или пропадания питания**, последние
  512 событий; во flash не пишется (D-019).
- События до синхронизации времени получают время задним числом после первой
  синхронизации NTP.
- Где смотреть: вкладка «История переключений» на веб-странице (`/history`) и команда
  консоли `history [N]` ([OPERATIONS.md](OPERATIONS.md)).
