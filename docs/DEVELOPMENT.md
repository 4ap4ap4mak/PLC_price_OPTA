# Разработка

## 1. Инструменты

| Инструмент | Зачем | Установка |
|---|---|---|
| VS Code + PlatformIO IDE | сборка, прошивка, монитор порта | расширение `platformio.platformio-ide` |
| PlatformIO Core (`pio`) | то же из командной строки | ставится вместе с расширением или `pip install platformio` |
| MinGW-w64 (WinLibs, GCC 16.2, UCRT) | компилятор хоста для unit-тестов `env:native` | `winget install -e --id BrechtSanders.WinLibs.POSIX.UCRT` |
| Git | контроль версий | репозиторий `github.com/4ap4ap4mak/PLC_price_OPTA` (приватный) |

После установки MinGW **перезапустите VS Code**, чтобы новый `PATH` подхватился
терминалом PlatformIO. Проверка: `g++ --version` в новом терминале. Если терминал
(например, Git Bash агента) не видит `g++`, добавьте путь вручную перед `pio test`:

```sh
export PATH="$LOCALAPPDATA/Microsoft/WinGet/Packages/BrechtSanders.WinLibs.POSIX.UCRT_Microsoft.Winget.Source_8wekyb3d8bbwe/mingw64/bin:$PATH"
```

Компилятор лежит в
`%LOCALAPPDATA%\Microsoft\WinGet\Packages\BrechtSanders.WinLibs.POSIX.UCRT_Microsoft.Winget.Source_8wekyb3d8bbwe\mingw64\bin`,
этот путь добавлен в пользовательский `PATH`.

**Одна копия PlatformIO.** `pio` в `PATH` — копия из расширения VS Code
(`%USERPROFILE%\.platformio\penv\Scripts`, 6.2.0; путь добавлен в пользовательский
`PATH` 2026-10-20). Вторую копию через `pip` не ставить: у разных версий разная
контрольная сумма проекта, и каждая при сборке очищает `.pio/build/opta` другой —
сборка падает с `Fatal error: can't create .pio\build\opta\...: No such file or
directory`. Проверка: `pio --version` выводит ту же версию, что и расширение.

## 2. Сборка и прошивка

```sh
pio run -e opta                  # сборка
pio run -e opta -t upload        # прошивка по USB (DFU)
pio device monitor -b 115200     # Serial-монитор
pio run -e opta -t clean         # очистка
```

Окружение `opta`: платформа `ststm32`, плата `opta` (ядро M7), фреймворк Arduino mbed.
Внешние библиотеки — ArduinoJson 7 и (только `env:opta`) `arduino-libraries/ArduinoMqttClient` 0.1.8 для Home Assistant (D-043).

Если загрузка не находит плату, дважды быстро нажмите RESET: Opta перейдет
в режим загрузчика, после чего повторите `upload`.

## 3. Unit-тесты

```sh
pio test -e native               # все тесты на ПК
pio test -e native -f test_planner   # один набор
```

- Тестируется только код из `lib/` (чистое ядро без Arduino). `env:native` собирает
  только `lib/` и `test/`, без `src/` (поэтому `pio run` без `-e` собирает лишь прошивку:
  `default_envs = opta`).
- Тесты — в `test/test_<модуль>/test_main.cpp`, фреймворк Unity. Флаги
  `-Wall -Wextra`: новых предупреждений быть не должно.
- Общие помощники — `test/helpers/TestHelpers.h`: `utc(...)` и `riga(...)` (местное
  время Риги → epoch), `fillHours(...)` (ряд цен по часам), `quietConfig()` (канал
  без сценариев), `ASSERT_ENUM` (сравнение `enum class`); `test/helpers/FakeKv.h` —
  KVStore в памяти с управляемыми ошибками (`testing::FakeKv`).
- Реальные ответы Elering — `test/fixtures/EleringFixtures.h` (строковые константы,
  сохранены 2026-10-20): двое суток, сутки перехода на зимнее время 2025 (25 часов,
  196 слотов) и пустой ответ на будущие даты.
- Тест `test_bug_kiNNN_*` фиксирует **текущее неверное** поведение из
  [KNOWN_ISSUES.md](KNOWN_ISSUES.md). Исправляя баг, перепишите тест под новое
  поведение в том же коммите и переименуйте его (без `bug_`).

| Набор | Что покрывает |
|---|---|
| `test_rigatime` | календарь, DST 2024–2026, несуществующее и повторяющееся местное время, форматы |
| `test_prices` | ряд слотов, порядок, поиск по времени, склейка со вчерашними ценами, агрегация в часы |
| `test_channelconfig` | значения по умолчанию, проверка, побайтная раскладка блоба, миграция v2/v3/v4 |
| `test_planner` | выбор 15-минутных интервалов, фиксация по всему окну, смена настроек посреди окна, сдвиг к концу окна, окна через полночь и в сутки перехода времени, отпуск 10 ч, пробуждение до минуты, совпадение плана и решения (KI-005), флажок старого блока ничего не включает (KI-004), название режима |
| `test_elering` | разбор реальных ответов, отказы, актуальность цены (KI-015), порядок слотов, пути прогноза и вчерашних цен |
| `test_httpparse` | строка запроса и заголовок `Content-Length` (особенности монолита), поля формы и их особенности, query, выбор страницы только из своего запроса и адрес возврата (KI-010), форма `/save` и ее ошибки, поле `force_hours`, форма `/force` |
| `test_dnspacket` | ответы captive DNS и mDNS, отказ на поврежденные пакеты |
| `test_history` | кольцевой буфер переключений, время событий до NTP, формат времени |
| `test_forceon` | таймер принудительного включения: полный срок, перезапуск, остановка, переполнение `millis()`, формат оставшегося времени |
| `test_configstore` | загрузка настроек из KVStore (фейк в памяти): ключа нет, текущий формат, сброс некорректного канала, миграция v3, поврежденный блоб, неизвестный размер, ошибки чтения и записи; учетные данные Wi-Fi |
| `test_userbutton` | кнопка USER: антидребезг, короткое и долгое нажатие, нажатие при включении, переполнение `millis()` |
| `test_controller` | `Controller` с фейковыми часами, выходами, ценами и логом: решение при новой цене и до NTP, устаревший timestamp, граница 15 минут и сброс ручного режима, повтор раз в 30 с, пересчет по минутам (пробуждение), сохранение прогноза при сбое и вчерашние цены, failsafe только для автоматики, ручной режим и принудительное включение (отмена друг другом, перезапуск, истечение с ценой и без, переполнение `millis()`), сохранение настроек и решение после него без запроса прогноза (KI-011), истечение отпуска отдельным шагом и лог плана только при изменении (KI-013) |
- Перед изменением поведения сначала пишется тест, фиксирующий **текущее** поведение
  (характеризационный), затем тест на новое поведение.

Обязательные случаи для времени и планировщика: переходы на летнее и зимнее время
(23 и 25 часов в сутках), полночь, окно через полночь, окно с границами не на
15 минутах, прогноз только на сегодня (ожидание цен), перезагрузка посреди окна
(новое `PlannerState`), смена настроек посреди окна, отрицательные цены.

Хелперы `test_planner`: `resetPrices`/`setPrice`/`commit` собирают прогноз по
интервалам, `fresh()` — состояние «после загрузки», `decideAt()` строит план и
решение, `simulate()` проживает окно по интервалам и считает включенные.

## 4. Ветки и коммиты

- `main` — проверенная на железе версия.
- Одна задача — одна ветка: `fix/...`, `refactor/...`, `feature/...`, `docs/...`.
- В `main` сливается только после того, как пользователь проверил прошивку на устройстве.
- Сообщения коммитов на английском, в повелительном наклонении
  (`Extract planner into lib/planner`).
- Рефакторинг и изменение поведения — разные коммиты и, по возможности, разные ветки.

## 5. Чек-лист изменения

1. Есть ли пункт в [KNOWN_ISSUES.md](KNOWN_ISSUES.md) или решение в
   [DECISIONS.md](DECISIONS.md)? Если поведение реле не описано — спросить пользователя.
2. `pio run -e opta` собирается без новых предупреждений.
3. `pio test -e native` проходит.
4. Обновлены документы:
   - поведение реле → [SCENARIOS.md](SCENARIOS.md);
   - кнопки, индикация, консоль, веб → [OPERATIONS.md](OPERATIONS.md);
   - API, маршруты, flash → [INTERFACES.md](INTERFACES.md);
   - модули → [ARCHITECTURE.md](ARCHITECTURE.md);
   - баги → [KNOWN_ISSUES.md](KNOWN_ISSUES.md);
   - раздел «Текущее состояние» в [CLAUDE.md](../CLAUDE.md).
5. Для пользователя — список того, что проверить на железе.
6. Изменились поля `ChannelConfig` (`lib/channelconfig`)? Новая версия, миграция,
   тест на старый блоб; `test_blob_layout_is_frozen` должен упасть — это сигнал.

## 6. Стиль кода

- C++17, отступ 4 пробела, `camelCase` для функций и переменных, `PascalCase` для
  типов, `UPPER_SNAKE_CASE` для констант (как в текущем коде; в новых модулях
  допустимо `kCamelCase` для `constexpr`).
- Комментарии на русском. Объяснять **почему**, а не что делает строка.
- В начале каждого нового файла — короткий комментарий: назначение модуля, от чего
  зависит, какие гарантии дает (потокобезопасность, блокирует ли).
- Нет динамической памяти в горячем пути. `String` — только в веб/консольном слое
  до его переписывания.
- Сравнения времени: `millis() - start >= interval`, никогда `millis() >= deadline`.
- Логи с префиксом `[TAG]` (список — [OPERATIONS.md](OPERATIONS.md) §8).

## 7. Проверка на железе (что просить у пользователя)

Минимальный набор после любой прошивки:

1. Лог загрузки: `[CONFIG]`, подключение Wi-Fi, `[NTP]`, первая цена, `[WATCHDOG]`.
2. Страница `http://opta-settings.local` открывается, график рисуется на вкладках
   «Вчера», «Сегодня», «Завтра»; открывается «История переключений».
3. Сохранение настроек одного реле → `[DECISION]` и `[RELAY]` в логе.
4. Короткое нажатие USER переключает реле 1.
5. Отключение роутера → через 1 час `[FAILSAFE]` (можно временно уменьшить
   `PRICE_FAILSAFE_TIMEOUT_MS` в тестовой сборке).

## 8. Версии и релизы прошивки (D-038)

Устройство обновляется с последнего релиза GitHub ([INTERFACES.md](INTERFACES.md) §6).
Релиз выпускает агент, когда пользователь просит или когда изменения уже проверены
на железе.

1. Повысить версию в [src/FirmwareVersion.h](../src/FirmwareVersion.h) (`X.Y.Z`):
   исправления — `Z`, новые функции — `Y`, несовместимые изменения (например, формат
   настроек без миграции назад) — `X`. Отдельный коммит `Bump firmware version to X.Y.Z`.
2. Отправить коммит в `origin`.
3. `scripts/release.sh X.Y.Z [notes.md]` (Git Bash; нужны `pio` и `gh` в `PATH`):
   проверяет версию в исходнике, чистое дерево и что коммит есть в `origin`, собирает
   `env:opta`, пишет `manifest.json` (размер, SHA-256) и создает релиз `vX.Y.Z` с
   `firmware.bin` и `manifest.json`. Без файла описания — описание из коммитов.
4. Релиз сразу становится «последним» — все устройства увидят его при следующей
   проверке. Ставить его будут только по кнопке. Для пробы, которую видеть не должны,
   релиз можно перевести в pre-release (`gh release edit vX.Y.Z --prerelease`): `latest`
   его не отдает.

Откат: релиз с ошибкой — удалить (`gh release delete vX.Y.Z --cleanup-tag`) или
выпустить следующий патч. Уже обновленное устройство возвращается на старую версию
только по USB (версию ниже установленной устройство по сети не ставит).

Проверка обновления на железе (кроме §7):

1. Прошить по USB версию A, выпустить релиз версии B > A.
2. «Проверить обновление» → «доступна новая версия B»; в логе `[FIRMWARE] Последний
   релиз: B…`.
3. Включить принудительное включение — кнопка «Обновить» неактивна, `firmware install`
   отклоняется. Остановить.
4. «Обновить» → прогресс на панели, в логе `[FIRMWARE] Загружено 25%…`, `Образ B
   записан и проверен`, `Установка версии B…`; реле в это время работают как обычно.
5. После перезагрузки: `[FIRMWARE] Версия B`, настройки реле и Wi-Fi на месте, панель
   «установлена последняя версия».
